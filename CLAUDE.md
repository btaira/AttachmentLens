# CLAUDE.md

Guidance for Claude Code (and future AI sessions) working in this repository.

## Project

AttachmentLens — a personal Flask app for journaling and AI-assisted reflection on
attachment-style patterns in imported Facebook posts. Single-file app (`app.py`,
~2000 lines), server-rendered Jinja templates, SQLite storage, optional Claude API
integration for analysis/generation.

- `app.py` — routes, auth, DB access (raw `sqlite3`, no ORM)
- `templates/` — Jinja templates
- `static/` — CSS/JS/images
- `posts.db` — SQLite database, **tracked in git** (deliberate; not a generated
  artifact — see "Database" below)
- `.secret_key` — Flask session-signing key, auto-generated by `app.py` next to the
  DB on first run. **Never commit this file.**
- `tests/` — test case docs (`functional/`) and runners (`runners/`)
- `docs/` — deployment/setup docs, published via GitHub Pages
- `scripts/` — one-off `.bat`/`.py` utility scripts

## Commands

```bash
python app.py                    # Flask dev server, http://localhost:5000
python dev_server.py             # alt dev server (works around a Flask/Waitress /stats 500 bug)
docker-compose up --build        # Gunicorn in Docker; mounts ./posts.db into the container
python tests/runners/comprehensive_test.py   # core functional tests (app must be running)
python tests/runners/extended_tests.py       # extended/edge-case tests
python tests/runners/user_flow_tests.py      # end-to-end flow tests
```

## Database

`DB_PATH` env var overrides the default `posts.db` at repo root (see `app.py`).
Locally and in `docker-compose.yml`, the DB lives at the repo root and is bind-mounted
directly (`./posts.db:/app/posts.db`) — **not** in a `data/` subdirectory. Render
deployment (`render.yaml`) mounts a persistent disk at `/app/data`, which is unrelated
to any local `data/` folder — don't recreate one; a previous version of this app used
that layout and left behind a duplicated `data/` dir and stale docs, since removed.

## File hygiene (read this before adding files at the repo root)

This repo has twice accumulated significant clutter from AI coding sessions leaving
behind their own status reports and debug output. Avoid repeating it:

- **Don't commit debug artifacts.** No ad-hoc screenshots, HTML response dumps, or
  `*.log` files. Use the scratch space your tool provides, or a gitignored path.
  Patterns like `debug_*.html`, `*_debug.png`, `*_ERROR.png`, `*.log` are gitignored
  — use them, don't fight them.
- **Don't write "summary"/"verification"/"complete" report files as deliverables.**
  Things like `CLEANUP_SUMMARY.md`, `VERIFICATION_REPORT.md`, `*_IMPLEMENTATION.md`
  describing work you just did are noise the moment they're written — the git log and
  PR description are the record of what changed and why. If a doc is genuinely
  reusable reference material, it belongs under `docs/` with a name describing its
  *subject*, not its status.
  - The one exception: `tests/functional/*.md` (canonical test case definitions) and
    dated files under `test_runs/` (gitignored — local test output only).
- **One canonical script per job.** Don't add a second test runner or helper script
  that duplicates an existing one under a slightly different name
  (`tests/runners/README.md` documents which scripts are current).
- **Root stays minimal.** `README.md`, `TODO.md`, `CLAUDE.md`, and deploy configs
  (`Dockerfile`, `docker-compose.yml`, `render.yaml`, `netlify.toml`, `Procfile`) only.
  Substantive docs go in `docs/`; keep only one doc per topic (check for an existing
  file before adding a new one — e.g. Docker instructions live solely in
  `docs/DOCKER.md`).
- **Never commit secrets.** `.secret_key`, `.env`, and anything under `data/` are
  gitignored — if a file like this shows up in `git status` as addable, that's a bug,
  not something to `git add -A` past.
